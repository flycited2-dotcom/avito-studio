# Спорадический краш 0xC0000409 в тестах (Windows/PySide6) — что известно

Дата: 2026-07-15. Машина: desktop TLT-1, Windows 11, Python 3.13.9, PySide6 6.11.1 и 6.8.3.

## Симптом
Полный прогон `pytest tests` иногда убивается fail-fast'ом `0xC0000409`
(STATUS_STACK_BUFFER_OVERRUN) без каких-либо сообщений Qt/faulthandler — чаще всего
на `test_publish_deploys_when_confirmed`. Изолированно этот тест НЕ падает (0 из 20):
нужен «затор» из накопившихся QThread'ов/deleteLater'ов предыдущих тестов, который
разом обрабатывается внутри очередного `waitSignal`.

## Это НЕ регрессия кода
Нетронутый master крашится так же: 4 из 12 прогонов (PySide6 6.11.1), 7 из 12 (6.8.3).
На ноутбуке владельца сюита стабильно зелёная — проявление зависит от машины/тайминга.

## Замеры вариантов run_in_thread (полная сюита, N прогонов)
| Вариант | Крашей |
|---|---|
| master как есть (без deleteLater у worker) | 4/12 |
| worker.finished→worker.deleteLater + closeEvent (ТЕКУЩИЙ) | 2/12 |
| thread.finished→worker.deleteLater («канонический» Qt) | 15/15 |
| принудительный дренаж DeferredDelete в conftest после каждого теста | 11/15 |
| worker.moveToThread(main) в конце run() | 8/15 |
| gc.disable() на всю сюиту | 7/12 |

Вывод: удаление QObject'ов, чья аффинность указывает в мёртвый/умирающий поток, —
источник; «канонический» вариант постит deleteLater в уже остановленный loop и
детерминированно валится. Текущий вариант (deleteLater внутри ЖИВОГО loop'а worker'а)
— лучший из замеренных. Полного нуля не даёт ни один паттерн ⇒ подозрение на
рантайм PySide6/shiboken на Python 3.13 в teardown-штормах.

## Практика
- Упавший прогон перезапускать; краш не связан с конкретным тестом.
- `MainWindow.closeEvent` дожидается фоновых потоков — это же защищает боевое
  приложение при закрытии окна во время операции.
- Если станет блокером: попробовать Python 3.12-venv и/или прогон по файлам
  отдельными процессами.
